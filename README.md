# DBCP (Database Course Project) — система учёта грузов торгового порта

Микросервисное приложение для учёта судов, грузов, складских мест и грузовых операций:
gRPC-сервис с бизнес-логикой, REST-gateway и веб-интерфейс. Поднимается одной командой.

Курсовой проект по дисциплине «Проектирование и разработка баз данных»
(09.03.04 «Программная инженерия»), доведённый до рабочего состояния и контейнеризованный.

`Go 1.25` · `gRPC` · `Protocol Buffers` · `PostgreSQL` · `chi` · `React 19` · `TypeScript` · `Docker Compose`

---

## Запуск

```bash
git clone https://github.com/deadsnxcks/database-course-project.git
cd database-course-project
docker compose up -d --build
```

Открыть **http://localhost:3000**

Одна команда поднимает PostgreSQL, накатывает миграции, собирает и запускает оба Go-сервиса
и веб-интерфейс. Устанавливать Go, Node, PostgreSQL или protoc на машину не требуется.

```bash
make up      # то же самое
make logs    # логи всех сервисов
make down    # остановить
make down-v  # остановить и удалить данные
```

## Архитектура

Браузер не умеет говорить по gRPC напрямую, поэтому между фронтендом и сервисом стоит
gateway: принимает REST, вызывает gRPC-методы, отдаёт JSON. Наружу опубликован один порт —
3000. nginx раздаёт статику и проксирует `/api/` на gateway, поэтому браузер видит единственный
origin и CORS не нужен.

**Почему монорепозиторий.** Сервис и gateway используют общие protobuf-контракты (`protos/`).
В раздельных репозиториях правка контракта требовала бы двух согласованных коммитов, между
которыми сервисы рассинхронизированы. Здесь это один атомарный коммит.

```text
.
├── server/          gRPC-сервис: бизнес-логика и работа с БД
├── gateway/         REST → gRPC
├── web/             React + TypeScript + Vite
├── protos/          контракты и сгенерированный код — общие
├── migrations/      SQL-миграции
├── docker-compose.yaml
├── go.mod           один Go-модуль на оба сервиса
└── Makefile
```

### Как устроена обработка ошибок

Сквозная схема, ради которой сделан отдельный слой доменных ошибок:

| Слой | Что делает |
|---|---|
| `storage` | переводит ошибки драйвера (`pgx.ErrNoRows`, код `23505`) в свои sentinel-ошибки |
| `services` | переводит их в доменные ошибки с категорией (`KindNotFound`, `KindConflict`, `KindInUse`, `KindUnprocessable`) |
| gRPC-перехватчик | по категории выбирает код ответа и пишет один лог на вызов |
| `gateway` | переводит код gRPC в HTTP-статус в единственном месте |

Домен не знает ни про gRPC, ни про HTTP — категория ошибки описана в его собственных терминах.
Благодаря этому маппинг живёт в одном месте вместо `switch` в каждом из 35 обработчиков,
а ожидаемый отказ (404, 409) пишется в лог как `Debug` и не поднимает ложных алертов.

## Предметная область

Торговый порт: суда доставляют грузы, грузы размещаются по складским местам,
над грузами выполняются операции.

**`vessel` — судно.** Название (уникальное), тип и максимальная грузоподъёмность.
Одно судно перевозит много грузов.

**`cargo_type` — тип груза.** Название (уникальное) и стоимость обработки тонны.
Справочник, на который ссылаются и грузы, и складские места.

**`cargo` — груз.** Название, вес, объём, ссылки на тип груза и на судно, которое его
доставило. Каждый груз обязательно принадлежит какому-то типу и какому-то судну.

**`storage_loc` — складское место.** Ограничения по весу и объёму, ссылка на допустимый
тип груза и ссылка на размещённый груз. Последняя допускает `NULL` — это и есть признак
свободного места. Рядом хранится дата размещения.

**`operation` — операция.** Название и время создания. Погрузка, выгрузка, перемещение.

**`operation_cargo` — связь операции с грузами.** Таблица многие-ко-многим с составным
первичным ключом из двух внешних: одна операция затрагивает несколько грузов, один груз
участвует в нескольких операциях. Собственного идентификатора у связи нет, поэтому в API
она адресуется парой ключей.

Целостность обеспечивается на уровне БД: внешние ключи между всеми связанными таблицами,
ограничения `CHECK` на положительность веса, объёма и грузоподъёмности, уникальные индексы
на названиях судов и типов грузов.

Правила размещения груза — свободно ли место, подходит ли тип, влезает ли по весу и
объёму — реализованы атомарными SQL-запросами: `UPDATE ... WHERE cargo_id IS NULL AND ...`
исключает гонку между проверкой и записью без явной транзакции.

## API

REST-эндпоинты gateway. Через nginx доступны с префиксом `/api` (например `GET /api/vessel`).

| Ресурс | Методы |
|---|---|
| `/vessel` | `GET` `POST` · `GET` `PUT` `DELETE` `/{id}` |
| `/cargotype` | `GET` `POST` · `GET` `PUT` `DELETE` `/{id}` |
| `/cargo` | `GET` `POST` · `GET` `PUT` `DELETE` `/{id}` |
| `/operation` | `GET` `POST` · `GET` `PUT` `DELETE` `/{id}` |
| `/storageloc` | `GET` `POST` · `GET` `PUT` `DELETE` `/{id}` · `POST /{id}/use` · `POST /{id}/reset` |
| `/opercargo` | `GET` `POST` `DELETE` |
| `/report-cargo-detail` | `GET` — детализация по грузам |
| `/report-cargo-type` | `GET` — сводка по типам грузов |

`/storageloc/{id}/use` и `/reset` — занять и освободить место. `/opercargo` работает
с составным ключом, поэтому пути с `{id}` там нет.

**Формат ответов.** Списки всегда массив, даже пустой. Даты — строки RFC3339 в UTC.
Ошибки — `{"code": "NotFound", "message": "vessel not found"}` с соответствующим HTTP-статусом.

**gRPC-сервисы** (`protos/proto/`): `VesselService`, `CargoTypeService`, `CargoService`,
`OperationService`, `OperationCargoService`, `StorageLocationService`, `ReportService`.

## Разработка

```bash
make run-server     # запустить gRPC-сервис локально
make run-gateway    # запустить gateway локально
make migrate-up     # накатить миграции
make gen-proto      # сгенерировать код из .proto
```

**Конфигурация.** Оба сервиса читают YAML по пути из `CONFIG_PATH` (`cleanenv`).
В репозитории лежат `docker.yaml` для контейнеров и `local.example.yaml` как образец —
скопируй в `local.yaml` и подставь свои значения; реальные `local.yaml` не отслеживаются.
Для локального запуска нужен `.env` (см. `.env.example`).

**Логирование.** `log/slog`: в `local` — цветной текстовый вывод, в `dev` и `prod` — JSON,
пригодный для сбора в Loki. Один запрос — одна строка лога: на сервере это gRPC-перехватчик,
в gateway — HTTP-middleware. Бизнес-слой ошибки не логирует, только оборачивает через `%w`,
поэтому в логе видна полная цепочка вызова.

**Protobuf.** Изменяемые поля в `UpdateRequest` объявлены как `optional` — это единственный
способ в proto3 отличить «поле не передали» от «передали пустое значение».

## Ограничения и планы

- **Тестов нет.** Архитектура к ним готова: интерфейсы объявлены на стороне потребителя,
  сервисы не зависят от конкретного хранилища, заглушка пишется вручную без генераторов.
  Начинать стоит с table-driven тестов сервисного слоя и `httptest` для gateway.
- **CI нет.** Напрашивается GitHub Actions: `go vet`, `golangci-lint`, `go build`,
  `npm run build`. Последнее особенно — фронтенд какое-то время не собирался из-за ошибки
  типов, и узнать об этом было неоткуда.
- **Тип судна — строковое поле, а не справочник.** В курсовой принято допущение, что тип
  судна не ограничивает перевозимые грузы. Нормализованный вариант — таблица `vessel_type`
  и связь многие-ко-многим с `cargo_type`, по аналогии с тем, как это сделано
  для складских мест через `storage_loc.cargo_type_id`.
- **Аутентификации нет.** В интерфейсе есть разделы оператора и склада, но проверки прав нет.
- **`DELETE /opercargo` принимает тело запроса.** Стандартом не запрещено, но часть прокси
  и клиентов тело у `DELETE` отбрасывают. Корректнее было бы передавать составной ключ
  параметрами строки запроса.
- **Тестовых данных нет.** После первого запуска база пустая; сид-файл с демо-данными
  сделал бы проект нагляднее сразу после `docker compose up`.
